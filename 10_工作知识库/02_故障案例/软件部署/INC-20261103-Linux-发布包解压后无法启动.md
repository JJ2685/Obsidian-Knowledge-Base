# 发布包解压后程序无法启动（符号链接被压成 0 字节文件）

## 0. 结论摘要
- **问题现象**：发布包解压到 `/opt/tn-frequency-release/` 后程序报 `error while loading shared libraries: libQt5WebEngineWidgets.so.5: file too short`。
- **直接影响**：现场无法安装运行。
- **根本原因**：已确认——不是配置问题：发布包在 Windows/NTFS/网盘环境转手时符号链接无法保留，被展开成 **0 字节普通文件**（134 个，其中 125 个运行时必需）。
- **最终处理**：脚本按"同名最长非空文件"重建 116 个符号链接；swrast_dri.so 无真身但系统有备份可忽略。
- **当前状态**：已解决。
- **可复用方案**：[[RB-Linux-发布包符号链接自检]]

## 1. 问题背景
- **问题发生前做过什么操作**：在 Windows 上归集、打包（193MB tar.gz），再上传服务器解压。
- **是否可以稳定复现**：是（Qt 发行版符号链接极多，Windows 打包必丢）。

## 2. 现象与复现步骤
```bash
cd /opt/tn-frequency-release && DISPLAY=:0 ./tn-frequency.sh
# error while loading shared libraries:
# /opt/tn-frequency-release/qt-lib/lib/libQt5WebEngineWidgets.so.5: file too short
```
> `file too short` 是动态链接器读到长度不足以构成 ELF 头的文件时抛的，几乎等同于"空文件"。

## 3. 排查过程
| 顺序 | 排查假设 | 执行操作 | 观察结果 | 判断 |
|---|---|---|---|---|
| 1 | 依赖缺失 | `find -type f -size 0` 按目录统计 | qt-lib/lib 109 个、qt-runtime 16 个、dri 1 个空文件 | 支持 |
| 2 | 符号链接丢失 | 检查 .so 链 | 链接名还在，指向关系全丢 | 确认 |

Qt 库的三层链接结构（打包后全毁）：
```
libQt5Core.so -> libQt5Core.so.5 -> libQt5Core.so.5.15 -> libQt5Core.so.5.15.2（真身 7MB）
```

## 4. 实际解决过程
对每个 0 字节的 `libX.so[.N[.N]]`，在同目录找名字最长且非空的 `libX.so.Y.Z` 作目标重建软链（Python 脚本，见 [[RB-Linux-发布包符号链接自检]]）。

- 实测：116 个成功重建，1 个 SKIP（dri/swrast_dri.so 无真身，系统自带可忽略）。
- 注意：凝思 6.0.80 自带 Python 3.4 不支持 f-string，脚本只能用 `%` 格式化。

修复后正常日志：
```
[AppConfig] loaded: UdpServerIP= "192.168.0.252" ... UdpListenPort= 11002
DevTools listening on ws://127.0.0.1:7777/...
```

## 5. 验证结果
- [x] `ldd` 无 "not found"（LD_LIBRARY_PATH 正确时）
- [x] 程序启动，窗口正常（1920×1007 最大化，导航齐全）
- [x] 曲线区空白为网关未推数据，非程序故障
- [x] 未引入新的异常（swrast_dri.so 不处理，启动脚本未设 LIBGL_DRIVERS_PATH）

## 6. 回滚方案
- 重新打包时在 Linux 上做，或用 zip（原生 UTF-8 文件名）替代 tar.gz。

## 7. 经验总结
- **这次最关键的判断依据**：`.so` 报 `file too short` ≈ 空文件，第一反应就该 `find -size 0`，不要查 LD_LIBRARY_PATH/ldd/GLIBC。
- **下次优先检查什么**：发布包落地 Windows 后 `find . -type l | wc -l`（Linux 原版 Qt 应有一两百个，为 0 就是全丢了）。
- **不建议重复尝试的操作**：在 Windows 上用 tar/zip 打包 Linux 程序集；靠 `test -x` 在 Windows 验证 Unix 权限。
